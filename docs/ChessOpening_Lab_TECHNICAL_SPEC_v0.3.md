# ChessOpening Lab — техническое задание (редакция 0.3)

**Статус:** проектное ТЗ, реализация не начата в рамках этого документа.  
**Текущая среда:** только домашний сервер.  
**Последующий релиз:** VPS, отдельная ветка развёртывания.  
**Приоритет:** технически полноценный MVP прежде аккаунтов, платежей и рекламы.

## 1. Цель и границы

Разработать адаптивное веб-приложение для изучения шахматных дебютов. Визуальная концепция: стартовый экран с двумя крупными режимами «Исследовать» и «Тренировать», сверху зарезервировано место для баннера. На каждом экране шахматная доска слева (на мобильном — сверху), информационная панель — справа (на мобильном — ниже). Пользователь может перемещать фигуры мышью и касанием; правила соблюдаются полностью.

### MVP включает

- Исследование дебютов на доске: все легальные ходы, история, возврат к позиции, цветовая подсветка ходов выбранной фигуры (союзные — синим, вражеские — красным), рестарт.
- Смена стороны (белые/чёрные) с обязательным сбросом партии; доска разворачивается.
- Выбор дебюта из каталога и тренировка вариативных продолжений; компьютерные ответы берутся из дебютного дерева, а не из Stockfish.
- Большая база дебютов: названия, ECO, варианты, транспозиции, альтернативные продолжения, проверенные идеи, ловушки и типичные ошибки.
- Правая панель: название дебюта/варианта, популярные допустимые продолжения с частотой появления и, по готовности, серверной оценкой позиции после каждого хода. Оценка с точки зрения белых, отдельно отображается мат.
- Показатель winrate **только на уровне дебюта/именованного варианта**, а не для отдельного хода; доля ничьих, выборка, метод и источник указываются явно. Выдача winrate будет скрыта до подключения PRO на коммерческом этапе.
- Серверный Stockfish с пулом ограниченного размера, предварительным анализом известных позиций и кешем Redis + PostgreSQL.
- Документированный импорт и проверка данных.
- Развёртывание на домашнем сервере через Docker Compose, базовый мониторинг и резервное копирование PostgreSQL.

### Не входит в технический MVP

Регистрация и авторизация, личный кабинет, избранное по аккаунту, платежи, автопродление, рекламные объявления (кроме плейсхолдера), аналитика пользователей, мобильные приложения, Redis/Celery-очередь, отдельный VPS. Эти функции описаны в ROADMAP.md.

## 2. Технологии и модули

- Frontend: React + TypeScript + Vite; react-chessboard (доска); chess.js (легальность и история), Zustand при наличии обоснованного состояния.
- Backend: Python 3.13 + FastAPI + Pydantic, SQLAlchemy 2 async + Alembic; python-chess для PGN/FEN/UCI.
- Engine: нативный Stockfish Linux, фиксированная версия и параметры анализа. Работает **на домашнем сервере**, никогда не скачивается в браузер.
- БД: PostgreSQL, источник истины для дебютов, аннотаций, статистики и долговременных оценок движка.
- Hot cache: Redis (отдельный контейнер); кеш не является источником истины.
- Web/HTTPS: Caddy, Docker Compose. Нет обязательных платных API и нет GPU.
- Тесты: pytest, Vitest, Playwright. Миграции — Alembic.

## 3. Данные

### Источники

1. `lichess-org/chess-openings` (CC0) — каталог именованных дебютов и вариантов.
2. Открытые архивы партий Lichess (CC0 согласно условиям источника) — реальные продолжения, частота и результаты партий. Загружаем офлайн и агрегируем потоково; сырые полные архивы не храним на домашнем production-инстансе.
3. Открытые шахматные задачи Lichess — кандидаты в ловушки, требующие проверки движком и экспертной ревизии.
4. Собственные аннотации по идеям, планам, ловушкам и типовым ошибкам; нельзя просто копировать чужие авторские объяснения.

### Модель данных (логическая)

- `openings(id, eco, name, slug, source, ...)`
- `opening_variations(id, opening_id, name, san_line, ...)`
- `positions(id, position_key UNIQUE, canonical_fen, ...)`
- `position_moves(id, from_position_id, uci_move, san_move, to_position_id, games_count, ...)`
- `variation_positions(variation_id, position_id, ply, ...)` — привязка именованных вариантов к позициям.
- `opening_statistics(opening_id/variation_id, filter_key, white_wins, draws, black_wins, sample_count, source_version, ...)`
- `opening_ideas`, `opening_traps`, `opening_mistakes` — локализованные, верифицированные карточки с привязкой к позициям/вариантам, вариантами решения и происхождением.
- `engine_evaluations(position_id, engine_version, analysis_profile, multipv, score_cp/mate, principal_variation, depth, analyzed_at, ...)`
- `import_runs(id, source, version, status, counts, errors, started_at, finished_at, ...)`.

Индексируем позиции, рёбра графа, имя/ECO дебюта, оценки и версии импорта. Транспозиции ведут в одну и ту же позицию. Ключ позиции содержит расположение фигур, сторону хода, права рокировки и актуальность взятия на проходе; счётчики FEN не используются для сопоставления дебютных позиций. Конкретный алгоритм нормализации тестируется на транспозициях и правах рокировки.

**Критерии данных:** 100% записей именованных дебютов исходного датасета импортированы или документированно отклонены; все сохранённые UCI-ходы легальны из соответствующей позиции; статистика дедуплицирует партии; покрытие ходов измеряется на независимой выборке, целевой ориентир ≥95% взвешенного покрытия популярных дебютных продолжений. «Полнота» означает покрытие каталогизированных дебютов и практически значимых вариантов, а не всех возможных шахматных партий.

## 4. Серверный Stockfish

- Отдельный модуль `AnalysisService` и `EnginePool` в Backend; UCI через python-chess.
- Число процессов задаётся через `STOCKFISH_WORKERS`. Начать с 1 процесса; 2 только при достаточных CPU/RAM и после замеров домашнего сервера.
- Каждому процессу задаются `Threads=1`, `Hash` (ориентир 64–128 MiB), лимит на выполнение запроса, до 3 PV. Параметры и тайм-ауты конфигурируемые.
- Пул создаётся один раз на единственный процесс-владелец. Не включать несколько Uvicorn workers, каждый с собственным EnginePool; при необходимости масштабирования вынести EnginePool в отдельный сервис.
- При каждом ходе сначала запрашиваем подготовленную оценку. Если её нет, используется ограниченный живой анализ. При занятости всех процессов **нет скрытого бесконечного ожидания и нет очереди**: `503 ANALYSIS_BUSY` с `Retry-After`, а доска/дебютная база продолжают работать.
- Для одной позиции одновременно вычисляется один и тот же профиль анализа (защита от stampede на уровне приложения; при расширении — распределённый lock через Redis).
- После завершения результаты сохраняются в PostgreSQL и кладутся в Redis. При прерывании клиента расчёт может быть отменён по политике сервера; устаревшие результаты интерфейс не отображает.
- Не обещаем фиксированную силу анализа при лимите времени: показываем глубину, версию и признак готовности.

## 5. Redis: обязательная часть MVP

Redis используется **только как кеш и при необходимости для короткоживущих блокировок**, но не как очередь.

### Стратегия чтения: cache-aside

1. `GET` по ключу в Redis.
2. При промахе — чтение PostgreSQL.
3. При отсутствии рассчитанной оценки — запрос к свободному Stockfish (если пользователь имеет право на анализ в текущем этапе).
4. Результат записывается в PostgreSQL, затем в Redis и возвращается клиенту.
5. Отказ Redis не должен останавливать приложение: fallback к PostgreSQL и ограниченному Stockfish.

### Ключи и TTL (первоначальные настройки)

- `opening:v1:{slug}` — метаданные, TTL 24 часа.
- `moves:v1:{position_key}:{dataset_version}` — частые продолжения, TTL 24 часа.
- `eval:v1:{engine_version}:{analysis_profile}:{position_key}` — подготовленная оценка с PV, TTL 7 суток (долговременная запись хранится в PostgreSQL).
- `stats:v1:{opening_id}:{filter_key}:{dataset_version}` — агрегаты дебюта, TTL 24 часа; платная статистика не должна быть публично доступна только по ключу Redis.
- `analysis-lock:v1:{analysis_key}` — кратковременный lock с TTL, только если потребуется при параллельных одинаковых запросах.

Настройки: `maxmemory` ориентировочно 128–256 MB (по фактической RAM), `maxmemory-policy allkeys-lfu`, отдельная Docker-сеть, без публичной публикации порта 6379. Можно отключить дисковую персистентность Redis, поскольку все ценные данные хранятся в PostgreSQL. Версионирование ключей защищает от устаревших данных после обновления импортов и версии движка. Показатели: hit/miss ratio, evictions, used_memory, p95 latency.

## 6. Минимальный HTTP API

- `GET /api/v1/openings?query=&eco=&page=` — каталог.
- `GET /api/v1/openings/{id}` — дебют, варианты, подтверждённые идеи/ловушки.
- `POST /api/v1/positions/resolve` — валидация FEN, нормализация и получение id известной позиции.
- `GET /api/v1/positions/{id}/moves` — популярные продолжения, названия именованных вариантов и текущие доступные оценки; у каждого хода частота и число партий, но не winrate хода.
- `POST /api/v1/analysis` — оценка известной/допустимой дебютной позиции: hit Redis/PostgreSQL или ограниченный живой анализ; статус готово/занято/неизвестная позиция.
- `GET /api/v1/openings/{id}/traps` — проверенные ловушки и линии.
- `GET /health/live`, `GET /health/ready` — здоровье процессов и зависимостей.

Контракт возвращаемых оценок: `position_id`, `score_cp` или `mate_in`, `side=white`, `depth`, `engine_version`, `analysis_profile`, `pv`, `source=cache|db|live`, `status`. Фильтры рейтинга/контроля времени для статистики — следующий релиз при наличии подтверждённых данных.

## 7. UX и поведение

- На главной две крупные кнопки режимов, сверху резерв места под рекламу без реального рекламного скрипта.
- В режиме исследования пользователь делает любые легальные ходы. На известных позициях справа показываем 3–8 популярных продолжений (по факту наличия), имя варианта, популярность, оценку Stockfish; карточки идей и ловушек.
- В режиме тренировки пользователь выбирает дебют, сторону, вариант. Ответ соперника выбирается из имеющихся дебютных продолжений. После отклонения от целевой линии — объяснение и возможность повторить; допустимые транспозиции засчитываются.
- **Цветовая подсветка ходов фигур (оба режима):** при выборе своей фигуры клетки её доступных ходов отмечаются **синим**; при выборе фигуры соперника потенциальные клетки её ходов отмечаются **красным**. «Своя/вражеская» определяется выбранной пользователем стороной (белые/чёрные), а не цветом фигур по умолчанию; при смене стороны цвета подсветки переопределяются. Для фигуры стороны, которой сейчас принадлежит ход, показываются строго легальные ходы по `chess.js`. Для другой стороны допускается только *предварительный просмотр* при условной передаче ей хода, рассчитанный на отдельной копии позиции: он не является разрешением сделать ход и не должен выдаваться за достоверный прогноз следующего хода. Это подсветка возможных перемещений, **не карта атак**. Выбор/снятие выбора фигуры, рестарт, смена стороны, переход по истории и фактический ход обновляют или очищают маркеры без мутации партии, FEN или истории при одном лишь просмотре. На десктопе и мобильных устройствах маркеры должны быть различимы не только цветом (форма/обводка); взятия визуально отличаются от обычного перехода.
- При смене стороны вся партия сбрасывается, при рестарте возвращаем стартовую позицию выбранного режима. История ходов не перескакивает и сохраняет легальность.
- При отсутствии оценки — «Не проанализировано», при занятости движка — «Анализ временно занят». Никогда не выдаём вымышленную оценку.
- На мобильном браузере доска работает касанием; отдельные нативные приложения в MVP не создаются.

## 8. Развёртывание только на домашнем сервере

Docker Compose: `frontend` (статическая сборка под Caddy), `api`, `postgres`, `redis`, `caddy`; Stockfish установлен/упакован для вызова из API с фиксированными правами. Подготовка данных — отдельная CLI-команда/разовый контейнер, не постоянный фоновый обработчик.

Сетевой доступ к PostgreSQL и Redis только внутренний. При публичном тестировании — HTTPS, ограничения запросов, защита админских endpoints; для личного тестирования можно закрыть доступ VPN. Секреты — в локальных env/secrets вне Git. Резервное копирование БД регулярно, проверка восстановления обязательна. Параметры CPU, RAM, диска и сети домашнего сервера пока неизвестны; поэтому ёмкость и число движков фиксируются после профилирования, а не угадываются.

Файлы инфраструктуры:

- `infra/compose.yaml` — общие сервисы;
- `infra/compose.home.yaml` — домашние параметры;
- `infra/compose.vps.yaml` — добавляется при публичном релизе;
- `infra/Caddyfile`, `infra/env.home.example` — настройки без секретов.

## 9. Репозиторий и ветки

- `main` — общая разработка и протестированный продуктовый код.
- `deploy/home` — домашнее развёртывание, создаётся сейчас; получает изменения из `main` после quality gate.
- `deploy/vps` — **не создавать до отдельного релиза VPS**. После создания это вторая ветка окружения наряду с `deploy/home`; обе используют одну кодовую базу и отличаются конфигурацией, а не реализацией бизнес-логики.
- Короткоживущие `feature/*` и `fix/*` по задачам. Не вести две независимые реализации модулей для home/VPS.

## 10. Проверка качества и Definition of Done MVP

Функциональные AC:

- AC-01: все легальные ходы, взятие на проходе, рокировка, превращение пешки, шах/мат/пат проверяются тестами.
- AC-02: рестарт и смена стороны сбрасывают партию; доска ориентируется правильно.
- AC-03: каталог импортирован, граф не содержит нелегальных переходов и корректно поддерживает транспозиции.
- AC-04: статистика дебютов выводится только с источником и размером выборки; статистика по отдельным ходам не выдаётся как winrate.
- AC-05: идеи/ловушки привязаны к верным позициям и их линии проходят шахматную валидацию.
- AC-06: Redis hit не вызывает SQL для оценки или процесс Stockfish; Redis down не ломает базовые сценарии.
- AC-07: при занятых движках API быстро возвращает `ANALYSIS_BUSY` без бесконечной очереди; повторный одинаковый запрос не создаёт неоправданное дублирование анализа.
- AC-08: домашнее развёртывание воспроизводимо, все health checks проходят, SQL и Redis закрыты от внешней сети.
- AC-09: автоматические frontend/backend тесты, нагрузочный тест для домашней конфигурации и проверенное восстановление резервной копии.
- AC-10: при выборе союзной фигуры доступные ходы подсвечиваются синим, при выборе вражеской — красным; относительно выбранной стороны. Проверены обычные ходы, взятия, рокировка, взятие на проходе, превращение, шах/связка, выбор фигуры вне очереди (только предварительный просмотр), смена стороны, рестарт, история и мобильное касание. Подсветка не меняет очередь хода, позицию, историю и не позволяет выполнять нелегальные ходы; красные ходы не обозначаются как карта атак.

Проверки Codex для backend: `pytest`, `ruff check .`, `black .`, `pre-commit run -a` (если настроен). Для frontend: TypeScript check, lint, Vitest и Playwright. После изменений — отчёт с изменёнными файлами, шагами проверки и рисками. Никаких секретов в логах, PR или документации.

## 11. Открытые вопросы (не блокируют проектирование)

- CPU, RAM, свободный SSD и операционная система домашнего сервера.
- Будет ли домашний MVP доступен всем в интернете или только тестовой группе.
- Нужны ли несколько языков интерфейса в MVP (рекомендуется начать с русского).
- Приоритетный набор контролей времени и рейтингов для первой статистической выборки.

Пока эти данные не известны, используем конфигурационные параметры и безопасные значения по умолчанию, не предполагая конкретного железа.
